# Доказательства отладки и рефакторинга

Подготовлено 08.11.2026. Исторические описания не являются новым выполнением прежних экспериментов. Наличие исправленного кода подтверждается текущим снимком Git; промежуточные состояния внутри коммитов подтверждены сохранёнными логами, но не отдельными коммитами.

## 1. Большие массивы

**Проблема:** валидатор продолжал обход заведомо недопустимого options, создавая ошибки пропорционально длине. Дополнительно scoring собирал неограниченный Set выбранных ID, даже перед возвратом late.

**Обнаружение:** исторические проверки массивов 10 000 вариантов и 100 000 выбранных ID. [002-refactor-checks](../evidence/002-refactor-checks.txt) фиксирует 4 падения из 93; [003-refactor-checks](../evidence/003-refactor-checks.txt) — 8 падений первоначальных регрессий из 261 (не все связаны с массивами).

**Изменение:** question-validation.ts:141–147 добавляет одну OPTION_COUNT без обхода неверной длины; answer-scoring.ts:57–110 ограничивает вход 100 элементами до Set, уникальные ID шестью и длину ID 256 кодовыми единицами UTF-16. Превышения — типизированные ошибки; допустимые дубликаты сохраняются.

**Проверка:** tests question-validation.test.ts:139–189; answer-scoring.test.ts:469–588, 620–669. Текущий общий test повторён 08.11, результат указан в testing.md. Не утверждать постоянную сложность всей валидации произвольных строк: неограниченные text/image остаются вне этих ресурсных лимитов.

## 2. Неточное округление

**Проблема:** прямое number-выражение давало 57.49999999999999 вместо математических 57.5 и 871.4999999999999 вместо 871.5. Эталон уточнён пользователем: математически точное значение, половины вверх.

**Обнаружение:** исторический независимый аудит и две регрессии: calculateScore(100,5000,4400) → 58; calculateScore(1000,30000,12168) → 872. [003-refactor.md](../evidence/003-refactor.md), [лог](../evidence/003-refactor-checks.txt).

**Изменение:** exactScore, answer-scoring.ts:142–158. BigInt и рациональное binary64; (2A+B)/(2B), без произвольного epsilon. Параметры и публичный результат сохранены.

**Проверка:** answer-scoring.test.ts:448–467 и 589–618, включая дробные полуцелые значения, соседние binary64 и монотонность. Массовые исторические проверки перечислены в свидетельстве; их исходный временный генератор не сохранён в репозитории и в 005a не запускался.

## 3. Дедлайн UI и shared

**Проблема:** первоначальный UI завершал вопрос при t>=D, хотя утверждённое правило shared допускает t=D.

**Обнаружение:** исторические контролируемые проверки 29999 / 30000 / 30001 мс; [004-deadline-checks](../evidence/004-deadline-checks.txt) показывает 7 падений из 30 до исправления.

**Изменение:** App.tsx:28–88. Общий finish с синхронным settled; expireIfDue использует строго t>D; submit получает результат evaluateAnswer. При 0 сек. на точной границе есть пояснение; после D повторно проверяется фактическое время. Interval и visibilitychange согласованы; cleanup удаляет тот же обработчик.

**Проверка:** App.test.tsx:311–494 — границы, задержанные ticks, гонки и идентичность обработчиков. Историческая mutation без removeEventListener дала 2 ожидаемых падения при 28 успешных; [свидетельство](../evidence/004-deadline-fix.md). В 005a mutation заново не выполнялась.

## 4. Несогласованный pnpm-lock.yaml

**Подтверждённый Git-diff:** 7fc8f4d содержит @quiz/shared@workspace:\* в apps/web/package.json, но не в importer apps/web lockfile. Коммит 4ad431b от **08.11.2026** добавляет только три строки @quiz/shared/specifier/version link:../../packages/shared.

**Как обнаружено в 005a:** сопоставление manifests и git show. Дополнительно 08.11 во временном каталоге восстановлены только manifests и lockfile 7fc8f4d; pnpm install --frozen-lockfile --ignore-scripts --lockfile-only завершился exit=1 / ERR_PNPM_OUTDATED_LOCKFILE, указав ровно отсутствующий @quiz/shared. [Исходный новый эксперимент](../evidence/005a-lockfile-reproduction-2026-11-08.txt).

**Проверка исправления:** текущая pnpm install --frozen-lockfile успешна на 4ad431b; публичный GitHub API подтвердил CI #5 completed/success для этого SHA. Старый отказ CI и способ первоначального обнаружения пользователем не подтверждены отдельным скачанным логом; не приписывать ему новый эксперимент.

## 5. Подготовленные сценарии интерактивной отладки

**Статус: инструкции подготовлены, но в 005a интерактивная браузерная сессия с breakpoint не проводилась.** Headless-проход 04.11 — отдельная браузерная проверка, а не доказательство использования DevTools-breakpoints. Эти сценарии нельзя описывать в отчёте в прошедшем времени без нового фактического выполнения.

Запуск при доступном Chrome: Node из .nvmrc; pnpm --filter @quiz/web dev; открыть локальный URL; DevTools → Sources. Исходники доступны через Vite/source maps, искать файлы по имени (номера строк относятся к HEAD 4ad431b).

1. **Лимит массива.** Breakpoint question-validation.ts:141 и :153. После паузы в обработчике App.tsx:79 выполнить в Console текущего frame чистый вызов evaluateAnswer с копией question, заменив options на new Array(10000). Ожидается AnswerScoringError INVALID_QUESTION с OPTION_COUNT в questionErrors; участок обхода :153 не должен выполняться для этой копии. Сама демо-структура не меняется.
2. **Точное округление.** Breakpoint answer-scoring.ts:148 и :157. Выбрать правильный ответ первого вопроса после первых 6 секунд и отправить. В paused frame наблюдать elapsedMs и BigInt numerator/denominator. Для точных двух регрессий можно вызвать чистый exactScore(100,5000,4400) или exactScore(1000,30000,12168) в доступном module/frame scope; ожидаются 58 и 872. Это ожидаемые значения из автотестов, не записанный браузерный лог.
3. **Однократный результат.** Breakpoint App.tsx:30, :41 и :79. Выбрать ответ и отправить, затем после продолжения инициировать document.dispatchEvent(new Event('visibilitychange')). Проверить, что settled=true, результат не переписывается. Пауза DevTools влияет на прошедшее performance.now-время; точные D−1/D/D+1 воспроизводить автотестами, а не утверждать миллисекундную точность ручного нажатия.

Никакие ожидаемые значения этого раздела не являются новыми логами отладки. Форму колледжного отчёта следует дополнить только после реального исполнения и фиксации даты/шагов.
