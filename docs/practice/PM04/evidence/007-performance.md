## Методика и предел нагрузки

Python 3.13 standard library: http.client, ThreadPoolExecutor и time.perf_counter_ns. Нагрузка замкнутая (closed-loop): один последовательный исполнитель либо максимум четыре одновременно; без цели поддерживать заданный arrival rate. На каждую из четырёх комбинаций GET/POST × C1/C4 — три повтора по 50. Итого 600 измеряемых запросов, 300 GET и 300 POST. Прогрев отдельно: 10 GET + 10 POST, исключён из таблиц. Авторский POST одинаковый, 752 UTF-8 bytes, 2 вопроса (single/multiple), по 4 варианта, 30 сек / 1000 баллов. Каждый успешный POST создаёт новый синтетический квиз; GET читает один исходный ID с тем же составом.

API собран и работает через Node без watch, прямой loopback HTTP без TLS/Vite/browser. Время начинается внутри worker перед HTTP request и заканчивается после чтения всего ответа. Ожидание задачи в очереди executor не включено в индивидуальную latency; wall серии включает запуск/завершение пула и все запросы. HTTP keep-alive используется в thread-local соединении; первое соединение worker может быть включено в его latency. Пулы создаются заново для каждого параллельного повтора. Прогрев БД/API не равен прогреву каждого нового TCP worker.

Процентили nearest-rank: sorted[ceil(p*N)-1]. В сводке процентиль вычислен по объединению 150 исходных длительностей, а **не** усреднением трёх p95. Throughput=N/сумма wall_s соответствующих повторов, не 1000/p50 и не запросы/вся длительность сценария. Длительности включают все попытки, ошибок в итоговой серии ноль. Между повторами нет намеренных пауз; схема, данные и порядок ячеек одинаковы. Полный порядок в JSON.

## Ресурсы и условия

macOS 15.7.1 arm64, Apple M1 Pro (10 logical CPU), 16 GiB RAM. Node 24.22.2, pnpm 10.34.9, Prisma 6.19.0; Docker Engine 29.2.1, VM 2 CPU / около 1,91 GiB. PostgreSQL 17.6 Alpine ограничен 2 CPU / 512 MiB, отдельная временная БД. Существующие процессы не останавливались; фоновая нагрузка не устранена. Сведения среды получены в текущем прогоне, см. [baseline](007-baseline.md).

Сумма wall_s измеряемых ячеек: 1.665 с. ps снял 7 отсчётов API: RSS 100.27–125.48 MiB, %CPU 5.9–57.6. На macOS ps %CPU — усреднённый показатель процесса, не точный расход CPU каждой ячейки. RSS включает runtime/JIT/cache; рост в коротком прогоне не доказывает утечку.

Docker stats --no-stream дал 2 отсчёта: offset 1.008 с, CPU 20.61%, память 33.32MiB / 512MiB; offset 2.976 с, CPU 0.34%, память 33.74MiB / 512MiB. Второй отсчёт получен после завершения HTTP-ячеек, поэтому отражает в том числе спад нагрузки. Docker CPU/память контейнера не равны host ps/RSS и не сравниваются напрямую. Сэмплер имеет собственную стоимость; никаких выводов о ресурсе на отдельный endpoint по этим двум точкам не делается.

## Ограничения интерпретации

- Прогон длится секунды, N каждой серии 50. p95/max и throughput нестабильны; это baseline для одинаковой методики, не capacity/SLA, не доказательство 50 одновременных игровых участников из NFR-06.
- GET читает маленький кэшируемый по рабочему набору квиз; POST-набор растёт в течение серии. Нет больших квизов, разных пользователей, WebSocket, TLS, интернета или игрового таймера.
- p95 первого параллельного GET выше последующих. Новые соединения/прогрев/планировщик/семплеры могут влиять, но причина не профилировалась. Не приписывать это SQL без EXPLAIN/профиля.
- Отказ БД и восстановление выполнялись после измерений и в таблицу latency/rps не входят. Время восстановления — отдельная метрика до первого успешного GET, не deadline и не latency запроса.
- Ресурсных точек мало для поиска утечек и saturation. Нельзя экстраполировать результаты на production или считать рост throughput при C4 линейно масштабируемым.

## Воспроизведение и ошибка первого стенда

Команда: python3 scripts/diagnostics/007-baseline.py --date 2026-11-23 --requests 50 --repeats 3 после pnpm build. Требуемое окружение/изоляция — в [задаче](../../../tasks/007-maintenance-baseline.md). Скрипт ограничивает максимум 100 запросов/ячейку и 3 повтора; базовый параллелизм остаётся 1/4. Для следующей даты/серии указать отдельный --output и сохранить тот же payload/ресурсные лимиты.

В первом прогоне 600 запросов прошли, но восстановление не подтвердилось: Docker получил автоматически назначенный host port. Контрольный эксперимент stop/start отдельно показал 32777→32778. Исправление стенда закрепило выбранный свободный порт и проверяет его после restart; это не изменение приложения. Первый JSON и лог не удалены, в baseline он не включён. Предыдущий контейнер удалён через finally. Сеть БД восстанавливалась на том же URL во втором прогоне; данные сохранились.

Оговорка первого прогона: фактический host port после его restart не записан. Смена auto-port доказана отдельным контрольным экспериментом, а не восстановлена из отсутствующего лога первой попытки. Поэтому первый отказ не используется для заключения о дефекте приложения; второй прогон проверяет один и тот же URL явно.
