## Ограничение времени и ресурсов

Один вызов Prisma.$transaction с неизменяемыми SQL-литералами, без пользовательских параметров. Ожидание250, transaction1000, statement750 и HTTP1500 мс. Конкурирующие HTTP calls разделяют Promise; при HTTP timeout операция хранится до завершения, а не создаётся вторая. В mock-тесте два одновременных запроса503 дали одну underlying-операцию, поздний reject обработан, следующий успешный probe вернул200. В реальном pause ответы503 пришли в пределах2500 мс допуска теста. Это не твёрдая граница1500 при любом event-loop lag.

SET LOCAL затрагивает настройку только этой транзакции, SELECT1 не меняет таблицы. Новый endpoint не проверяет миграции/полноту схемы и не гарантирует готовность игровых комнат. Проверка SQL statement timeout750 на реально медленном SELECT не проводилась: реализация всегда SELECT1. Реально воспроизведено зависание транспорта к paused PostgreSQL.

## Утечки и доступ

Readiness возвращает только {status:ready/not_ready}; ошибки query/URL/SQL/stack не сериализуются. HTTP-корпуса из настоящего сценария проверены на тестовый пароль, DATABASE_URL, postgresql://, PrismaClient, query engine, stack. Mock-ошибка содержит SECRET/internal/SQL/stack и не попадает в ответ. Значение неверного PORT не печатается. Startup logs могут содержать стандартный локальный Nest stack конфигурации, но без URL/пароля; домашний путь обезличен в документах.

API сохранил bind127.0.0.1, PG опубликован только на127.0.0.1. Локальный enable-флаг не менялся, авторизация и доступ извне не добавлены. Vite получает только согласованный порт proxy, не DB credentials. Новые endpoint и тесты не требуют внешних зависимостей. Контракты и публичный GET квиза остались без isCorrect. Успешные benchmark GET/POST проверены тем же условием; это не утверждение о тайных данных в самостоятельном демоплеере, который не менялся.

Операции stop/start/pause/unpause выполнялись только с собственным случайно названным контейнером, без пользовательских volumes. После stop/start данные сохранены и API process не заменён; подтверждено и чтение, и запись. После pause проверен старый GET и ready. Это не power-loss тест и не гарантия отсутствия потери любой незавершённой записи.

## Оставшиеся вопросы для аудита

- Верхняя граница числа SQL: проверить single-flight, таймер cleanup и поздние ошибки, в том числе при реальном невосстанавливающемся blackhole. HTTP deadline не отменяет underlying запрос; он может удерживать одну connection дольше.
- Подобрать timeout по целевому окружению; локальные1500 не являются сетевым SLA. Readiness использует общий Prisma pool, поэтому перегрузка пула может дать503 даже при живой БД — это допустимая временная неготовность, но требует наблюдения под нагрузкой.
- Shutdown при зависшем Prisma-запросе и непрерывный высокий probe rate не проверялись. Не заявляется полное доказательство отсутствия утечек памяти по короткому прогону.
- readPort теперь явно десятичный: экспонента/hex не принимаются; пробелы вокруг допустимого числа разрешены, пустая строка не означает default.

Критических или существенных проблем в выполненных сценариях после изменения не обнаружено. Существующие ограничения auth/owner, production deploy и server idempotency не изменились. Независимый аудит рекомендуется до commit. №009 не начата.
