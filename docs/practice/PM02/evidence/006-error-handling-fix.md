## Воспроизведение до исправления

Сначала добавлены регрессионные тесты, quiz-api.ts ещё не изменён. Команда pnpm --filter @quiz/web test завершилась с кодом 1: 39 тестов упали, 58 прошли, всего 97. Это ожидаемые падения проверки дефектов, не выдаваемые за успешный прогон. В [006-error-handling-checks.txt](006-error-handling-checks.txt) сохранены команды, полные сообщения и exit codes.

1. Mock HTTP 201 возвращает DTO с пустым ID. Проверка typeof id === string принимает его. В UI hasSaved становится true, savedId остаётся пустым: нет ID/сброса, дальнейший save молча отклоняется. Пробелы и произвольные строки тоже принимались; отсутствующий ID отклонялся, но без обязательного предупреждения о возможной записи.
2. HTTP 413 с пустым/HTML-телом вызывает исключение response.json до обработки статуса. Вместо размера запроса показывался нечитаемый ответ. Аналогично терялась диагностика других HTTP-ошибок. POST с некорректным успешным DTO не предупреждал о возможной записи.

## Минимальное исправление

В quiz-api.ts корневой ID должен соответствовать UUID v4 с допустимым variant, без нормализации. Этот формат совпадает с ParseUUIDPipe API. Прочие строковые доменные ID вариантов не меняются. createQuiz не возвращает ошибочный DTO, поэтому существующая ветка QuizWorkspace, устанавливающая hasSaved, недостижима на повреждённом ответе. Сам компонент не менялся.

JSON разбирается безопасно: при нечитаемом теле body=undefined, но статус остаётся доступным. Для HTTP-ошибки сначала выбирается статусная семантика; только 400 + INVALID_QUIZ извлекает структурированные ошибки. Сырой HTML/JSON-текст ошибки не выводится. Для успешного ответа обязательны форма DTO и UUID. Для повреждённого успешного POST, а также POST 500/503 добавлено предупреждение: сервер мог сохранить квиз, но подтвердить результат не удалось; повторять создание без проверки нельзя. Для определённой ошибки 400 такое предупреждение не добавляется. Сетевой сбой сохраняет прежнее предупреждение о неизвестном результате.

Запрос не повторяется автоматически. UI после ошибки сохраняет введённые данные и снимает busy; пользователь может исправить поля/выполнить GET. Тест явного повторного действия используется для проверки отсутствия зависания, а не как рекомендация повторять неопределённый POST. Двойной submit при явном повторе отправляет один запрос.
