## 2. Некорректный ID успешного POST

Симптом: HTTP 201 с id="" принимался клиентом. Флаг hasSaved становился true, но savedId был пустым; ID и действие создания нового квиза отсутствовали, повторное нажатие ничего не делало. Причина — проверка только typeof id === string в runtime-границе успешного DTO. Пробелы/произвольный текст тоже проходили. Отсутствующий ID уже отклонялся, однако предупреждение о возможной записи было недостаточным.

Воспроизведение: fetch mock возвращает 201 и DTO с пустым, пробельным, отсутствующим или некорректным ID; UI-тест заполняет форму и нажимает «Сохранить». Это проверка повреждённого ответа, не утверждение, что Prisma реально генерировала пустой UUID. Источник: [протокол исправления](../evidence/006-error-handling-fix.md).

Исправление: [quiz-api.ts](../../../../apps/web/src/quiz-api.ts) проверяет UUID v4 до возврата createQuiz; формат соответствует ParseUUIDPipe API. Ошибка не достигает успешной ветки формы. Для повреждённого успешного POST показано предупреждение: сервер мог сохранить квиз, но подтвердить результат не удалось; повторять создание без проверки нельзя. Автоматического повтора нет. Исходные данные сохраняются, busy снимается. Backend и shared-контракты не менялись.

Регрессии: [quiz-api.test.ts](../../../../apps/web/src/quiz-api.test.ts) — корректный UUID и пять неверных ID, в том числе UUID другой версии; [QuizWorkspace.test.tsx](../../../../apps/web/src/QuizWorkspace.test.tsx) — четыре UI-варианта, отсутствие успеха, сохранение черновика, только явное действие и защита двойного submit. Полный [лог до/после](../evidence/006-error-handling-checks.txt).

## 3. Потеря HTTP-статуса при не-JSON теле

Симптом: 413 с пустым или HTML-телом выдавал «нечитаемый ответ» вместо превышения размера. Аналогично терялся смысл других HTTP-ошибок. Причина: исключение response.json прерывало выполнение до проверки response.ok/status. Сырой HTML пользователю не требовался.

Воспроизведение и исправление подтверждены теми же [регрессионными тестами](../../../../apps/web/src/quiz-api.test.ts) и [логом](../evidence/006-error-handling-checks.txt). При неудаче разбора body становится undefined, однако статус обрабатывается дальше. Только HTTP 400 + INVALID_QUIZ считается достоверной структурированной ошибкой валидации; 404 сохраняет смысл отсутствия квиза, 413 — размера, 503 — временной недоступности. POST 500/503 предупреждает о возможной записи. Сеть и повреждённые успешные ответы обрабатываются отдельно, без автоматического повтора.

Матрица: 5 статусов (400/404/413/500/503) × 3 тела (JSON/пустое/HTML) × 2 метода (GET/POST) = 30 тестов. Дополнительно проверены структурированный 400, ложный INVALID_QUIZ в 503, повреждённые успешные тела и сеть. Это mock-тесты, не новые реальные отказы PostgreSQL.
