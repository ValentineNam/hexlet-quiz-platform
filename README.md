# hexlet-quiz-platform

A real-time quiz platform developed as part of Hexlet College industrial internship (PM01, PM02, PM04).

Учебный проект Quiz Platform. Задача 001: каркас монорепозитория, стартовая страница и проверка работоспособности API. Полное ТЗ: [v1.0](docs/requirements/TECHNICAL_SPEC_v1.0.md). MIT-лицензия сохранена в LICENSE.

## Требования и запуск

Зафиксированы Node **24.22.2** (LTS) и pnpm **10.34.9**. Node 23 не поддерживается проектом. При установленном nvm переключите Node в текущем терминале (это не меняет системную установку):

```sh
nvm install
nvm use
corepack pnpm --version
```

Corepack должен быть установлен и поддерживать актуальные подписи pnpm. Все команды `pnpm` ниже также можно вызывать как `corepack pnpm`, без глобального `corepack enable`. Если Corepack отсутствует, установите pnpm 10.34.9 по официальной инструкции pnpm; установка глобальных инструментов не входит в bootstrap.

```sh
pnpm install --frozen-lockfile
pnpm dev
```

Frontend: http://127.0.0.1:5173. API: http://127.0.0.1:3000/health — HTTP 200, `{"status":"ok"}`. Остановка обоих процессов — Ctrl+C. Порты должны быть свободны. По умолчанию API работает без БД: маршруты квизов выключены (`ENABLE_QUIZ_API=false`), `/health` проверяет только liveness.

## Демонстрационное прохождение квиза (задача № 004)

После `pnpm install --frozen-lockfile` и переключения на Node из `.nvmrc`:

```sh
pnpm --filter @quiz/web dev
```

Откройте http://127.0.0.1:5173. API и PostgreSQL для демонстрации не нужны. `pnpm dev` также запускает демонстрацию вместе с API. Порт 5173 должен быть свободен; для другого порта используйте `pnpm --filter @quiz/web dev --port 5174`.

Три вопроса: одиночный выбор, множественный выбор и короткий вопрос на 5 секунд. Таймер начинается при появлении каждого вопроса. Выберите ответ, нажмите «Отправить ответ», изучите результат и перейдите дальше. По истечении времени начисляется 0. После итогов доступно «Начать заново». Обновление страницы сбрасывает прохождение, результаты не сохраняются.

Это локальная тренировка: правильные ответы и расчёт баллов находятся в браузере. В настоящей многопользовательской игре они должны оставаться на сервере до закрытия вопроса; клиентскому времени доверять нельзя. Контракты shared не менялись. [Описание задачи](docs/tasks/004-quiz-player-ui.md), [фактическая проверка размеров и клавиатуры](docs/testing/004-ui-check-2026-11-04.md).

## Локальная PostgreSQL (не обязательна для каркаса)

Нужны Docker Compose и запущенный Docker Engine:

```sh
cp .env.example .env
# Замените POSTGRES_PASSWORD в .env своим локальным паролем.
docker compose config -q
docker compose up -d postgres
docker compose ps
docker compose exec postgres pg_isready -U quiz_local -d quiz_local
docker compose down
```

Если Docker CLI не обнаруживает плагин `compose`, используйте установленную отдельную команду `docker-compose` вместо `docker compose`. В проверенной среде доступна именно она.

БД `quiz_local`, пользователь `quiz_local`, порт `127.0.0.1:5432`. Данные сохраняются в volume `postgres_data`; `down` их не удаляет. Пример пароля не является действующим секретом. Не публикуйте `.env`. Для подключения API используйте отдельную инструкцию ПМ02 ниже; локальный демоплеер по-прежнему не использует БД.

## ПМ02: локальная интеграция API и PostgreSQL (задача № 005)

Если `.env` уже существует, не перезаписывайте его. Добавьте параметры из `.env.example`: `DATABASE_URL` с пользователем `quiz_local`, вашей локальной БД и паролем, совпадающим с `POSTGRES_PASSWORD`. Специальные символы пароля в URL нужно percent-encode. Реальные значения не коммитить.

```sh
# После настройки .env; Docker Engine должен быть запущен:
docker-compose up -d postgres
pnpm --filter @quiz/api db:validate
pnpm --filter @quiz/api db:migrate
ENABLE_QUIZ_API=true pnpm --filter @quiz/api dev
```

Prisma CLI validate/migrate и процесс API загружают корневой `.env`; значения уже заданного окружения имеют приоритет. Генерация Prisma и сборка shared входят в команды API автоматически. После изменения кода shared пересоберите shared или перезапустите API-dev. Миграции при старте API не запускаются и данные не сбрасывают. PORT по умолчанию 3000, bind только 127.0.0.1.

Включаются `POST /quizzes` и `GET /quizzes/:id`. Авторский вход содержит правильные ответы; оба ответа API содержат только PublicQuizResponse без `isCorrect`. Пока авторизации нет, включайте эти маршруты только для локальных проверок. На этапе № 005 сетевого редактора ещё не было. Текущий редактор № 006 создаёт и читает квизы через Vite proxy; демоплеер остаётся отдельным локальным режимом. Без флага маршруты возвращают 404 и подключение БД не создаётся. При включённом флаге отсутствие URL/БД останавливает запуск. `/health` не является проверкой текущей доступности БД.

```sh
# Нужна отдельная БД с суффиксом _test и применённой миграцией.
# Задайте TEST_DATABASE_URL через окружение, не выводя credentials в общий лог.
pnpm --filter @quiz/api test:integration
```

Тесты делают записи: используйте выделенную тестовую БД. Они не вызывают reset/truncate и удаляют только собственные созданные записи. Обычный `pnpm test` использует mock HTTP-тесты и не требует PostgreSQL. CI дополнен отдельным PostgreSQL service для DB-набора. [Контракты, схема и ограничения](docs/tasks/005-api-database-integration.md), [журнал ПМ02](docs/practice/PM02/progress.md), [фактическая проверка PostgreSQL](docs/practice/PM02/evidence/005-integration.md).

## Создание и просмотр через API (задача № 006)

Настройте локальную PostgreSQL и `.env` по разделу интеграции № 005, запустите Compose и примените миграцию. Затем:

```sh
ENABLE_QUIZ_API=true pnpm dev
```

На http://127.0.0.1:5173 выберите «Создать и посмотреть квиз». Заполните название, описание, вопросы и варианты; отметьте правильные ответы. Вопросы можно добавлять, удалять и перемещать кнопками «Выше»/«Ниже». «Сохранить квиз» выполняет POST; после успеха показан ID. «Получить квиз» выполняет отдельный GET и показывает данные без правильности вариантов. Сохранённая форма заблокирована; для новой записи используйте «Создать другой квиз». По ID можно открыть и ранее сохранённый квиз.

Vite перенаправляет `/api/*` на loopback API, удаляя префикс `/api`. По умолчанию API — порт 3000. Если он занят, запустите оба процесса с согласованными портами:

```sh
PORT=3001 QUIZ_API_PORT=3001 ENABLE_QUIZ_API=true pnpm dev
```

`QUIZ_API_PORT` читается только конфигурацией dev-сервера Vite из окружения запуска, не из поля формы; PostgreSQL URL и пароль во frontend не передаются. Production proxy/deploy не настраивались. Предпросмотр production-сборки без proxy не является способом проверки интеграции.

Демопрохождение остаётся отдельным локальным режимом и не использует сохранённый GET для оценки ответов. Авторизации и серверной игры нет; API по-прежнему выключен по умолчанию и слушает только 127.0.0.1. При потере ответа POST факт сохранения может быть неизвестен — автоматических повторов нет. Черновик хранится в памяти страницы и теряется при смене режима/обновлении. [Архитектура и протокол № 006](docs/tasks/006-frontend-api-integration.md).

## Диагностика запуска и готовности БД (задача № 008)

`PORT` — непустое десятичное целое число 1–65535; окружающие пробелы удаляются. При отсутствии переменной используется 3000. Пустое, нечисловое, дробное или выходящее за диапазон значение останавливает запуск с сообщением о PORT, без вывода его содержимого. Привязка API остаётся `127.0.0.1`.

- `GET /health` сохраняет `200 {"status":"ok"}`: жив ли запущенный API, без запроса к PostgreSQL.
- `GET /ready` доступен только при `ENABLE_QUIZ_API=true`: `200 {"status":"ready"}` при успешном запросе к БД, `503 {"status":"not_ready"}` при ошибке/таймауте. При выключенном DB-модуле — 404.

```sh
# После настройки отдельной локальной БД и применения миграции:
ENABLE_QUIZ_API=true pnpm --filter @quiz/api dev
curl -i http://127.0.0.1:3000/health
curl -i http://127.0.0.1:3000/ready
```

Readiness выполняет `SELECT 1` внутри короткой Prisma-транзакции с локальным `statement_timeout` 750 мс, ожиданием транзакции 250 мс и её таймаутом 1000 мс. На общую DB-операцию создаются один результат и один HTTP-дедлайн 1500 мс с момента её запуска. Параллельные запросы используют этот результат; после дедлайна новые probes сразу получают 503, пока underlying операция не завершилась. Новых подписок к зависшему Prisma Promise не добавляется. После завершения операции состояние освобождается и следующая проверка может вернуть 200. Планировщик может добавить задержку. Таймаут не объявляется SQL-cancel; таблицы не изменяются, наличие всех миграций/готовность игры не проверяется.

Поведение подключения при старте не менялось: если включённый API не смог подключиться к PostgreSQL, запуск завершается, поэтому `/ready` ещё недоступен. Сценарий 503 относится к уже запущенному API. После возврата БД готовность проверяется заново без перезапуска API. [Реализация и результаты № 008](docs/tasks/008-startup-readiness.md).

## Ограниченная остановка API (исправление № 008a)

SIGTERM и SIGINT по-прежнему запускают штатные NestJS lifecycle hooks и отключение Prisma. Перед ними устанавливается process watchdog: общий дедлайн **5000 мс от первого сигнала**. Повторные/смешанные сигналы не продлевают его и не запускают второй shutdown. При успешном завершении Nest повторно посылает исходный сигнал; обычные коды сигналов сохраняются (в Python subprocess: -15/-2, в shell обычно 143/130). Unref-таймер не удерживает нормально завершившийся процесс.

Если любой асинхронный lifecycle hook, включая `$disconnect()`, завис, watchdog пишет только безопасный маркер `SHUTDOWN_DEADLINE` и принудительно завершает процесс с кодом **1**. Он охватывает всю последовательность hooks, а не только Promise.race вокруг Prisma. Ошибки отключения БД обезличиваются перед стандартным логированием Nest.

Пять секунд — фиксированный локальный предел: он оставляет запас относительно readiness-дедлайна 1,5 с и коротких операций, но не допускает бесконечного ожидания. Это новый явный fallback, **не гарантия завершения всех активных запросов**: после принудительной остановки результат незавершённого POST может быть неизвестен. JavaScript watchdog требует работающего event loop; синхронный dead loop требует внешнего supervision. Остальные сигналы сохраняют прежнюю обработку Nest. [Модель, регрессии и настоящий PostgreSQL](docs/tasks/008a-readiness-shutdown-fixes.md).
